## <u>Vectorization:</u>

A vector is a sequence of items of the same type: vector items can be
coerced to the same type based on the order of coercion :
character\>double\>integer\>logic. If you entered items of characters
and doubles in a vector, the whole vector items are coerced into
characters, if you have a vector of double and integers, it is coerced
to double in that order. Vectorization is faster in operations than
looping: Let’s demonstration

``` r
# example of vectors
g <- c("Joy","Steph","Mimmy")

l <- c(TRUE,FALSE,TRUE, FALSE)
```

### Recycling Rule :

operating on vectors of different length, the shorter one is recycled
into the longer one: The shorter vector should be a multiple of the
longer one to allow normal computation if added it takes the first
element in the short vector multiply it to the first item in the longer
vector, takes the second element in the shorter vector multiply it to
next element in the longer vector and repeats the process in the shorter
vector for all elements in the longer vector

``` r

b <- c(10,20)
a + b
```

## <u>Scope and Environments</u>

R uses lexical scoping a function looks for variables in the environment
where it was defined, not where it is called. If a variable is outside
the function creation environment or in the global environment we use
the \<\<- arrow to tell R to look upper the levels of environments from
the immediate environment up.

``` r
# let's demonstrate 
x <- 10

# let's create a function that assigns a differnet value to x and see if it changes the gloabal x value of 10
no_change <- function(){
  x <- 100
  return(x)
}
# let's call the function and then x and see if the values are all changed to 100
no_change()
```

    ## [1] 100

``` r
x
```

    ## [1] 10

You see that global x \<- 10 was unchanged because a function picks it
variables from the environment is it was created not where it was
executed. Now let’s create a function that can read the variable in a
global environment or a level up above where it was declared:

``` r
# let's create a counter variable and give it a value and update it from inside our function 
counter <- 0
increase_count <- function(){
  counter <<- counter +1
  return(counter)
}
# let's run an check what happens
increase_count()
```

    ## [1] 1

``` r
counter
```

    ## [1] 1

You see our function was able to look up above the creation environment
to pic the variable counter. Even though counter was not created in the
function environment. the \<\<- sign tells R to look up and find that
counter variable

## <u>Error Handling in Functions</u>

**What is Error Handling?**

Error handling means anticipating things that can go wrong in your
function and dealing with them gracefully instead of letting your
program crash.

R has three levels of problems

- `stop()` : throws an **error**, halts execution completely

- `warning()`: throws a **warning**, execution continues but flags
  something suspicious

- `message()`: prints an **informational message**, not an error at all

``` r
# let's demonstrate this 
divide <- function(a,b){
  if (!is.numeric(a) | !is.numeric(b)){
    stop("Numbers must be numeric to divide")
  }
  if (b == 0){
    warning("Dividing by Zero returns infinity\n")
  }
  if (a<0){
    message("You are dividing by negative")
  }
  return(a/b)
}
```

#### Using try Catch code:

The tryCatch is used to handle errors, the function has an expression
block and blocks to handle errors

and warnings and a final block to run regardless of whatever happens.

``` r
# let's try to find square root
square_root<- function(x){
  result <- tryCatch(
    expr = {
      if (!is.numeric(x)) {stop("You need to enter a numeric value")}
      sqrt(x)
    },
    error = function(e){
      cat('This error occured\n',conditionMessage(e))
      return(NA)},
    warning = function(w){
      cat('You got this warning\n',conditionMessage(w))
      return(NA)},
    finally = {cat('\nWe attempted to run sqrt')}
  )
  return(result)
}
```
